# IHISI SMI 通道：不用 H2OUVE 也能写在 Windows 上才能写的变量

这是本项目的第二条写入通道。第一条是 efivarfs（Linux 内核的 `SetVariable`），
在固件声明了写保护的变量上会被推进 `EFI_WRITE_PROTECTED`；这条通道绕过它，
直接把报文交给 SMM。

**它不依赖 H2OUVE、不依赖 Windows、不依赖任何内核模块** —— 但需要 root，
以及一个几十行的 C 调用器（用户态没法直接执行 `out` 指令）。

> 状态：协议已从 H2OUVE 主程序与 segwindrv 驱动逐条逆向出来，报文构造有 20 项
> 单元自检。**尚未在实机跑过一次真实写入**（见第 9 节）。

---

## 1. 为什么 `SetVariable` 不行，SMI 行

`SetVariable` 是 UEFI runtime service，调用时会进固件，固件检查这个变量是否允许
从 OS 侧写。`Setup` 这类 Setup 变量，Insyde 默认不允许 —— 返回
`EFI_WRITE_PROTECTED`，内核映射成 `EROFS`，于是你看到
`Read-only file system`（跟文件系统没关系，`open()` 是成功的，被拒的是 `write()`）。

SMI 是另一条路：`out` 指令到 SMI 端口，CPU 立刻切入 **SMM**（ring -2，特权比内核还高），
固件在 SMM 里执行处理程序。SMM 不看「这个变量是否允许 OS 写」——因为它不认为
请求来自 OS，而认为来自固件自己。H2OUVE 能改 `Setup`，靠的就是这个。

```
efivarfs:  用户 → 内核 → SetVariable → 固件检查 ACL → 拒绝 ✗
IHISI:     用户 → out <SMI_CMD> → SMM → 固件自己写自己 ✓
```

## 2. 三个必须知道的值

### 2.1 SMI 端口

来自 ACPI FADT 的 `SMI_CMD` 字段（偏移 `0x30`）。驱动里的写法是
`FindSmiCommadPort()`：解析 `RSD PTR ` 找到 RSDP，顺着 RSDT/XSDT 找到 `FACP` 表，
读其 `+0x30`。

本实现优先读 `/sys/firmware/acpi/tables/FACP` 的 `+0x30`（不需要 `/dev/mem`），
读不到才退回扫物理内存。两条路都失败时用 `0xB2` 并**显式标注这是假设值** ——
绝大多数 x86 平台的 SMI 端口就是 `0xB2`（APM_CNT），但假设不等于实测。

**本机实测是 `0xB0`，不是 `0xB2`**。这正是「必须从 FADT 读、不能猜」的理由：
拿错端口的话，`out` 不会报错，也不会有任何反应，症状和「SMM 不响应」一模一样。

### 2.2 IHISI 主功能号

**不是硬编码，是运行时扫出来的。** 驱动 `FindSmiMainFuncNum()`
（`init` 段 RVA `0x5680`）做的事是：

```
物理地址 0xF0000 起，64KB 范围，每 0x10 字节：
    比对 6 字节 "$IHISI"
    命中 → 取标签 +6 处的那个字节，就是主功能号
没找到 → 0xEF（无效值）
```

本机固件是 `0x64`。这个值有**两条独立证据**，一条静态一条动态：

1. **静态**（2026-10-30 新增）：把 `Cert_A7S_NAC.fd` 的 LZMA 压缩卷解开
   （`tools/fw_unpack.py`，得到 34 MB 的 `unpack/p1.fd`），在 `0x3DBA34`
   处有一串签名连排的数据：
   ```
   0x3DBA2C  "HFDM" "O2H$" "$IHISI" 0x64
   ```
   即固件自己的数据里就写着「`$IHISI` 后面跟 `0x64`」。
2. **动态**：驱动会在 F 段里扫到同样的 7 字节，取 `+6` 也是 `0x64`。

**但实机 2026-10-30 实测：F 段里扫不到 `$IHISI`。** 见第 7.1 节。
这说明两件事分开：值本身确定是 `0x64`，**能不能从 F 段读到它另说**。
驱动扫不到时用 `0xEF`，所以本工具也允许 `--func 0x64` / `--func 0xEF`
直接指定，不必非得让扫描成功。

注意 `$IHISI` 只出现在**解压后**的镜像里。在原始 `Cert_A7S_NAC.fd` 上搜
（`$IHISI`、`$IHI` 都是 0 处）会一无所获，因为 SMM / runtime 驱动住在
压缩卷里 —— 这也是上一版文档说「静态搜不到」的原因，那句话只对未解压镜像成立。

### 2.3 一块 4GB 以下的物理内存

SMM 通过 `ESI`/`EDI` 直接访问**物理地址**，绕过页表。所以必须：

- 拿一页匿名内存，`mlock()` 锁住（防换出）
- 从 `/proc/self/pagemap` 读出 PFN，算出物理地址
- 物理地址必须 `< 4GB`（`ESI`/`EDI` 是 32 位）
- 发 SMI 前**再核对一次** PFN（`mlock` 防不了内存迁移，compaction / NUMA balancing
  都可能搬页；PFN 一变，SMM 就会去读一块无关内存然后往 NVRAM 里写垃圾）

报文 760 字节，一页装得下，不需要物理连续的多页。

## 3. 报文格式

以 `Setup`（5 字符名，700 字节数据）为例，名称占 `N = 12` 字节（UTF-16LE 含结尾 NUL）：

| 偏移 | 长度 | 内容 |
|---|---|---|
| `0x00` | 16 | GUID，EFI 混合端序（前三段小端） |
| `0x10` | N | 变量名，UTF-16LE，含结尾 `0x0000` |
| `0x10+N` | 4 | `"$H2O"` |
| `0x14+N` | 4 | `"$Var"` |
| `0x18+N` | 4 | `"$Tbl"` |
| `0x1C+N` | 4 | 保留，0 |
| `0x20+N` | 4 | 数据长度（u32，本例 700 = `0x2BC`） |
| `0x24+N` | 4 | 变量属性（u32，`Setup` 是 `0x07` = NV\|BS\|RT） |
| `0x28+N` | 5 | 保留，0 |
| `0x2D+N` | 1 | 固定 `0x10` |
| `0x2E+N` | 2 | 校验和（u16） |
| `0x30+N` | 数据长 | 数据本体 |

总长 = `0x30 + N + 数据长`。本例 `0x30 + 12 + 700 = 760`。

### 校验和

**数据区全部字节之和的 16 位二进制补码**，使 `(sum + checksum) & 0xFFFF == 0`。

原函数（`H2OWriteVariable` @ `0x50850`）的实现方式看起来复杂：用 `bx` 累加偶数
字节、`di` 累加奇数字节，最后 `bx += di`，再 `not bx; inc bx`。但
`sum(偶) + sum(奇)` 就是全体字节之和（16 位寄存器自然溢出），所以等价于上面这句。
奇数长度时末尾那个字节单独加上。

注意：**不是**标准的 16 位字求和（那种要 `sum(lo) + 256*sum(hi)`）。这里高字节
没加权，就是纯字节累加。

## 4. 寄存器约定

`out dx, al` 那一刻的寄存器（驱动 RVA `0x3E78`）：

| 寄存器 | 值 |
|---|---|
| `AL` | IHISI 主功能号（本例 `0x64`） |
| `AH` | 子功能号（写变量是 **`0x01`**） |
| `EBX` | `"O2H$"` = `0x2448324F`，魔数，SMM 入口校验 |
| `ESI` | 报文物理基址 |
| `EDI` | 报文物理基址 + `0x10 + N`，即指向 `"$H2O"` |
| `DX` | SMI 端口 |
| `ECX` | 0 |

`out` 返回后 SMM 会改写寄存器。**执行结果看 `AL`（`EAX & 0xFF`）。**

依据是驱动自己的两处代码：

```asm
; 触发函数 @ 0x3E78
3e8f  mov ebx, [..0xD168..]    ; EBX = "O2H$"
3e95  mov al,  [..0xE37F..]    ; AL  = 主功能号  ← 覆盖掉 AH 里的子功能号
3e9b  mov dx,  [..0xE3C8..]    ; DX  = SMI 端口
3ea2  out dx, al               ; 只送 AL，AH 不出端口
3eb2  mov [r8+0x10], eax       ; out 之后的整个 EAX 写回寄存器块

; 调用者 @ 0x13F3A
13f3a call 0x3e78
13f3f mov  [rdi+4], eax
13f42 cmp  al, bl              ; AL == 0 → 成功
```

> 本文档上一版写的是「看 `DL`」，**是错的**。那个结论来自 H2OUVE 用户态
> `H2OIsSupportIhisi` 读输出块 `+0x10` 的写法，但输出块 `+0x10` 对应的是
> **EAX** 而不是 EDX（驱动 `0x3EB2` 明确把 EAX 存在 `[r8+0x10]`）。

**诊断价值**：如果回来的 `EAX` 仍是输入值 `(sub<<8)|main`（例如 `0x1064`），
说明 SMM **根本没碰过寄存器** —— 这不是「返回了错误码」，而是「这条 SMI
没有人处理」。工具会专门区分这两种情况并给出不同建议。

`EBX` 必须精确等于 `"O2H$"` —— 驱动每次 `out` 前都重设一遍，说明 SMM handler
在入口就校验这个魔数；不对直接拒绝。

## 5. 怎么用

分四步，风险从零递增。**每一步都先跑完再做下一步。**

### 第 1 步：探测（只读，不发 SMI）

```bash
sudo ./insyde-nvram ihisi --discover
```

预期：

```
SMI 端口   0xB0   （FADT.SMI_CMD (/sys/.../FACP+0x30)）
IHISI 主号 0x64   （$IHISI 标签物理 0xF0146，取标签 +6）
```

两个值都要能对得上。端口是假设值时会有明确提示。

**实机 2026-10-30 结果：端口 `0xB0` 拿到了，主功能号没扫到**（详见 7.1 ——
根因是 `/dev/mem` 给的 F 段是内核填充，不是固件）。这时工具会直接说明
「这份数据不可信」，并给出 `--func 0x64` 的完整命令，不会让用户误以为
固件没有这个标签。

### 第 2 步：握手（发一条无副作用的 SMI）

```bash
sudo ./insyde-nvram ihisi --ping              # 用扫到的主功能号
sudo ./insyde-nvram ihisi --ping --func 0x64  # 扫描失败时手指定
```

发的是子功能 `0x10`（`IsSupportIhisi`），它只回答「通道在不在」，不改任何状态。

- `AL == 0` → 通道确认可用
- 有响应但 `AL != 0` → 主功能号或端口不对（`0xFF` 通常意味着这条 SMI 没人接）
- 寄存器**原样不动**（`EAX` 还等于发送值）→ handler 没写用户态快照，
  不能区分「没进 SMM」和「进了但静默忽略」，见 7.2 / 7.4

### 第 2.5 步：原样写回（用真实报文，但不改内容）

```bash
sudo ./insyde-nvram probe --record Setup --via ihisi --func 0x64 --yes
```

这一步发的是**真正的子功能 `0x01`**，报文长度、GUID、名称、校验和、`ESI`/`EDI`
全都是真写时会用的那一套 —— 只是数据区填的是「现在读到的内容」。

- 返回 `VERDICT: WRITE_OK` + 回读一致 → 报文被 SMM 接受了，格式没问题
- 返回 `SMM 返回状态 0xNN` → 报文被拒，**此时去改值毫无意义**

它是整条链路里性价比最高的一步：成功什么都不改变，失败也没有副作用。
`--ping` 只测了 `0x10`（握手），这一步才测 `0x01` + 报文校验。

### 第 3 步：空跑（拼报文，拿物理地址，但不发 SMI）

```bash
sudo ./insyde-nvram apply patches/ftpm-enable-RMGCZ6T0P0909.patch --via ihisi --dry-run
```

会打印报文长度、`ESI`/`EDI`、属性，以及报文前 48 字节的十六进制。对照第 3 节
的表格自己核一遍偏移和魔数。

### 第 4 步：真写

```bash
sudo ./insyde-nvram apply patches/ftpm-enable-RMGCZ6T0P0909.patch --via ihisi
```

门禁、undo 副本、交互确认、写后读回校验，全部与 efivarfs 通道一致 ——
**只有最后那个「往下写」的动作换了**。写完后仍然通过 efivarfs 读回验证，
所以校验是真的在校验，不是自说自话。

## 6. 与 H2OUVE 的对应关系

| 环节 | H2OUVE（Windows） | 本项目（Linux） |
|---|---|---|
| 找端口 | `FindSmiCommadPort()` 走 `/dev/mem` 解 ACPI | 优先 `/sys/firmware/acpi/tables/FACP`，兜底 `/dev/mem` |
| 找主功能号 | `FindSmiMainFuncNum()` 扫 `0xF0000` | 同左，逻辑逐条对齐 |
| 拿物理内存 | 驱动 `IOCTL 0x2223C6` 分配 | 匿名页 + `mlock` + `pagemap` 取 PFN |
| 填报文 | `H2OWriteVariable` 拼缓冲 | `ihisi.build_packet()`，同一份布局 |
| 送进 SMI | 驱动 `IOCTL 0x2223D6`，内部 `out dx, al` | `ihisi_smi` 用内联汇编 `out` |
| 读变量 | `GetFirmwareEnvironmentVariableA` | efivarfs（不用改） |
| 枚举变量 | IHISI 子功能 `0x05` | 列举 efivarfs 目录（不用改） |

Linux 侧只需要子功能 `0x01`（写）；读和枚举走 efivarfs 更省事。

## 7. 失败排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `Permission denied: '/dev/mem'` | 非 root | `sudo` |
| `pagemap 返回 PFN=0` | 内核屏蔽物理帧号 | 需要 `CAP_SYS_ADMIN`；确认是 root |
| `物理地址在发 SMI 前被内核迁移了` | 页被搬走 | 重跑。多次复现就考虑大页 |
| `连续 N 次分配到的页都在 4GB 以上` | 高地址机器 | 缩小内存占用后重试 |
| `$IHISI 标签没找到` | 本机 `/dev/mem` 给的是内核填充，见 7.1 | 用 `--func 0x64` |
| `iopl(3) 失败: Operation not permitted` | 缺 `CAP_SYS_RAWIO` | `sudo` |
| `--ping` 无响应（寄存器原样不动） | handler 没写回快照，含义待定，见 7.2 | `tools/smi_probe` 看 0xB1 状态位 |
| `--ping` 的 `AL != 0` | 进了 SMM 但被判错 | 换 `--func 0x64` / `--func 0xEF` |
| 写入返回状态非 0 | 报文被 SMM 判非法 | 检查魔数、长度字段、校验和、GUID 端序 |

### 7.1 实机：F 段里扫不到 `$IHISI`

2026-10-30 在 TIMI A7S（BIOS `RMGCZ6T0P0909`）上以 root 实测：

```
SMI 端口   0xB0   ...（FACP+0x30 读得到）
主功能号  未取到：物理 0xF0000..0xFFFFF 里没有 $IHISI 标签
```

`/dev/mem` 的 `mmap` **成功了**（不是被拦），但按驱动的规则（`0x10` 步进、
6 字节比对）扫完 64 KB 没有命中。

**根因（第二轮实测确认）：读回来的 F 段不是固件，是内核填充。**

`sudo python3 tools/fseg_scan.py --out dump/` 的输出：

```
可读 1 段，共 131072 字节（占 100.0%）
  000e0000..000fffff  131072 B   非零 130559  0xFF 511  0x00 513
$IHISI 在可读区间里完全不存在
000F0000  1a 87 a0 f8 1e 87 e0 f4 ba 15 90 c3 be 15 d0 cf
```

对落盘的 `dump/fseg_000e0000_020000.bin` 做统计：

| 指标 | 实测 | 真固件应该是 |
|---|---|---|
| 熵 | **8.0000** bit/byte | 6–7 之间，填充区拉低 |
| 出现过的字节值 | **256 / 256**，每个约 512 次 | 大面积堆在 `0x00` / `0xFF` |
| 32 位字 `0x00000000` | **0 个** | 成百上千 |
| 32 位字 `0xFFFFFFFF` | **0 个** | 成百上千 |
| 重复 32 位字 | 16294 / 32768 | 更高（指令片段成片重复） |

真实的 128 KB 固件里空白填充是常态，全 0 / 全 1 的 32 位字不可能一个都没有。
完美均匀分布只有一种来源：内核在填。这台 CachyOS 7.3 的内核
（`CONFIG_STRICT_DEVMEM=y` + `CONFIG_IO_STRICT_DEVMEM=y`）对**非 RAM** 页
（F 段在 `/proc/iomem` 里是 `000f0000-000fffff : System ROM`）只给一份
占位数据，`mmap` 成功、读得到字节，但内容与硬件无关。

所以结论要分两步看：

- ✅ 主功能号 `0x64` 是**确定的** —— 静态在 `p1.fd @ 0x3DBA34` 处
  `"HFDM" "O2H$" "$IHISI" 0x64`，SMM handler 自己拼的报文魔数也在
  `p1.fd @ 0x58A9DC` 处得到印证；
- ❌ 「F 段里没有标签」**不能**作为反证 —— 那份数据本身不可用。

工具现在会在画像判定为 `looks_like_fill` 时直接说明这一点，并把
`--func 0x64` 的完整命令给出来，而不是让用户误以为固件没有这个标签。

要更彻底地找，跑：

```bash
sudo python3 tools/fseg_scan.py --out dump/     # 只读：F 段 + 签名搜索 + 画像 + 落盘
sudo python3 tools/fseg_scan.py --all           # 把 /proc/iomem 的小块保留区全扫一遍
sudo python3 tools/fseg_scan.py --peek          # 不读内存：端口归属 + FADT 字段
```

**注意**：`CONFIG_STRICT_DEVMEM=y` 下用户态没有任何办法拿到 F 段真实内容。
驱动能做到是因为它是内核态、走 `MmMapIoSpace`。这条差异是硬约束，不是代码 bug。

### 7.2 实机：`--ping` 回来时寄存器原样不动

2026-10-30 实测（root，端口 `0xB0` 来自 `FACP+0x30`，主功能号 `0x64` 来自命令行）：

```
发送子功能 0x10（IsSupportIhishi），不改任何状态 …
回写寄存器 eax=0x1064 ebx=0x2448324F ecx=0x0 edi=0x0 edx=0xB0 esi=0x0
```

`0x1064 = (0x10 << 8) | 0x64`，**正好是我们送进去的值**。`EBX` 也仍是 `"O2H$"`。
换成 `--func 0xEF` 再试，`eax=0x10EF`，同样是输入值。

**⚠ 本节初版的结论「CPU 没进 SMM」是错的，已撤回。**

初版推理：进了 SMM 的 handler 若接受会写 `AL=0`、拒绝会写错误码，
寄存器全原样说明 SMI 没人处理。这个推理漏了 SMI 的基本性质——
**SMI 是异步的**：`out` 之后 CPU 把寄存器快照存进 SMRAM，handler
跑完 `rsm` 从快照恢复。**handler 完全不碰快照时，用户态看到的
寄存器就原样不变**——它不需要「故意写回错误码」，什么都不做
就是原样。

后续 `port_peek` 实测（见 7.4）证明 `0xB0` **已解码且稳定回 `0xEF`、
`0xB1` 稳定回 `0x01`**，排除了「端口未解码」。「寄存器原样」现在
只有一种解释：**SMI 可能触发了，但 handler 没向用户态快照写任何东西**
——静默忽略、拒绝但不回错误码、或这条 SMI 归别的设备所有，都有可能。

判定「handler 是否真在跑」的正确办法是看硬件状态位：`0xB1` 是 APM
状态端口，handler 处理命令通常会翻转它。`tools/smi_probe` 就干这个。

### 7.4 实机：IO 端口解码扫描（port_peek）

2026-10-30 用 `tools/port_peek`（纯 `in`，不写端口、不发 SMI）扫描：

```
0xac..0xaf, 0xb2..0xbf   全 0xFF（稳定）     ← 未解码
0xb0                     ef ef ef ef ...      ← 稳定，已解码
0xb1                     01 01 01 01 ...      ← 稳定，已解码
```

对照组（校准「解码端口长什么样」）：

```
0x60 fa / 0x61 2c / 0x62 21 / 0x64 14    （键盘/EC，真值）
0x70 0a / 0x71 26 / 0x72 0b / 0x73 cd    （RTC/CMOS，真值）
```

结论：

- 本机「未解码」= 稳定 `0xFF`，不抖动 → 0xB0/0xB1 的稳定非 FF 值
  证明它们**已解码**
- `0xB0/0xB1` 是 APM 命令/状态端口对（AMD FCH；Intel 是 0xB2/0xB3，
  这也是为什么早期假设 0xB2 是错的——平台不一样）
- `0xB0` 读回 `0xEF`、`0xB1` 读回 `0x01` 的含义待 `smi_probe` 判定：
  回声（上次命令）/ 状态残留 / busy 位，三种都可能

### 7.3 为什么「写保护」和「SMM 不响应」很可能是同一件事

驱动里有两条完全不同的写入路径，而且**只有一条会被 `EFI_WRITE_PROTECTED` 挡住**：

| 路径 | 说明 | 受 NVRAM 写保护影响 |
|---|---|---|
| `SetFirmwareEnvironmentVariable`（走固件 runtime 服务） | 就是 efivarfs 干的事 | **会**，直接返回 `EFI_WRITE_PROTECTED` |
| IHISI SMI（子功能 `0x01`，绕过 runtime 服务直接进 SMM） | H2OUVE 的用法 | 设计上就是**绕开**写保护 |

本机 efivarfs 实测是 `EROFS`（= `EFI_WRITE_PROTECTED`），说明固件确实开了
NVRAM 写保护。而写保护一旦打开，部分 Insyde 版本会连带把 IHISI 的 runtime
入口一起关掉 —— 这正好解释了「端口对、功能号对、`EBX` 对，但 SMM 不理」。

最后一条要正视：H2OUVE 是通过内核驱动发的，而我们的 `iopl(3)` + `out` 也是从
CPL=3 发 —— 两者在 CPU 层面等价，区别只在**时序**（H2OUVE 驱动加载于 OS 运行时，
同样不是 boot services）。所以「runtime 不可用」这条其实站不住，更可能是前两条。

## 8. 固件侧证据（为什么这份报文布局可信）

报文布局是从 H2OUVE 主程序反汇编出来的。但「H2OUVE 这么拼」和「固件认这个格式」
是两件事。下面是独立证据：**固件自己也用同一套布局拼报文**。

在官方 BIOS 镜像 `Cert_A7S_NAC.fd` 里搜 `$H2O`，总共 2 处。看第一处
（文件偏移 `0x3E928`）的机器码：

```
0003e928  c7 44 24 30 24 48 32 4f   mov dword [rsp+0x30], 0x4F324824   ; "$H2O"
0003e930  c7 44 24 34 24 56 61 72   mov dword [rsp+0x34], 0x72615624   ; "$Var"
0003e938  c7 44 24 38 24 54 62 6c   mov dword [rsp+0x38], 0x6C625424   ; "$Tbl"
0003e940  c7 44 24 40 00 40 00 00   mov dword [rsp+0x40], 0x4000       ; 长度字段
0003e948  c6 44 24 4d 10            mov byte  [rsp+0x4D], 0x10         ; 固定字节
```

对齐关系：

- `$H2O` 起点 = `rsp+0x30`
- 长度字段 = `rsp+0x40` = `$H2O + 0x10` ✓ 与第 3 节表格一致
- 固定字节 `0x10` = `rsp+0x4D` = `$H2O + 0x1D` ✓
  对应表格里的 `0x2D + N`（`$H2O` 位于 `0x10 + N`，故 `0x2D+N - (0x10+N) = 0x1D`）

第二处（`0x5F540`）结构相同，只是栈偏移换成 `rsp+0x40`：

```
0005f540  c7 44 24 40 24 48 32 4f   "$H2O"
0005f544  c7 44 24 44 24 56 61 72   "$Var"
0005f548  c7 44 24 48 24 54 62 6c   "$Tbl"
0005f550  mov [rsp+0x50], ...       长度 @ $H2O + 0x10
0005f560  mov byte [rsp+0x5D], 0x10  固定字节 @ $H2O + 0x1D
```

**两个独立来源（H2OUVE 用户态 + 固件自身）指向同一套偏移**，这是目前能拿到的
最强静态证据。它确认了报文布局，但**仍然不构成运行时验证** —— 见下一节。

### 8.1 解压后的镜像：SMM 侧的校验代码

上面两处都是**调用方**（客户端拼报文）。真正的验收方在压缩卷里。用
`tools/fw_unpack.py` 把 LZMA 卷解开（`p1.fd`，34 MB）后，`$H2O` 出现在
`0x58A9DC`，这次是 `cmp` 而不是 `mov`：

```
0058a9c6  b9 2d 00 00 00             mov  ecx, 0x2D
0058a9cb  e8 ...                     call 取缓冲区
0058a9d4  80 7b 1d 10                cmp  byte [rbx+0x1D], 0x10      ; ← 固定字节
0058a9d8  74 07 / b8 13 80 00 00     je 跳过 / mov eax, 0x8013       ; ← 不对就返回 0x8013
0058a9dc  81 3b 24 48 32 4f          cmp  dword [rbx],    0x4F324824 ; "$H2O"
0058a9e1  75 16                       jne  失败
0058a9e3  81 7b 04 24 56 61 72       cmp  dword [rbx+0x04],0x72615624 ; "$Var"
0058a9e8  75 0d                       jne  失败
0058a9ea  81 7b 08 24 54 62 6c       cmp  dword [rbx+0x08],0x6C625424 ; "$Tbl"
0058a9ef  75 04                       jne  失败
0058a9f1  33 c0                       xor  eax, eax                    ; 返回 0 = 通过
```

这一段同时给出三件事：

1. **`$H2O` / `$Var` / `$Tbl` 在 `+0` / `+4` / `+8`** —— 与我们的报文一致
   （我们把 `EDI` 指向 `$H2O`，从那里数就是这三个偏移）。
2. **固定字节必须在 `+0x1D`，值必须是 `0x10`** —— 错了返回 `0x8013`。
3. 魔数不匹配返回 `0x8000000000000002`（`mov rax, 0x8000000000000002`）。

这是**固件在验收报文**的直接证据，比「固件也拼过报文」更强一档。

### 8.2 主功能号的静态出处

同一份 `p1.fd` 里 `$IHISI` 只有 1 处（原始未解压镜像里 0 处），在 `0x3DBA34`：

```
003dba2c  48 46 44 4d  "HFDM"
003dba30  4f 32 48 24  "O2H$"
003dba34  24 49 48 49 53 49 64  "$IHISI" 0x64
```

固件数据自己把 `0x64` 摆在 `$IHISI` 后面第 6 个字节 —— 正是驱动
`FindSmiMainFuncNum()` 要取的那个位置。这是 `0x64` 的直接出处。

## 9. 已知限制（诚实清单）

1. **未在实机验证过真实写入。** 协议、报文、寄存器约定都是从二进制里逐条读出来的，
   报文构造有 20 项自检，但 `out` 之后 SMM 到底认不认，只有跑一次 `--ping` 才知道。
   本项目的开发环境拿不到 `/dev/mem` 与 `CAP_SYS_RAWIO`，这一步必须由你在真实
   root shell 里完成。
2. **报文必须在一页内。** 760 字节没问题；如果哪天要写的变量超过约 4000 字节，
   就需要物理连续的多页，当前会明确报错而不是偷偷失败。
3. **SMM 侧是黑盒。** 真正执行写入的 handler 在 BIOS 的 SMM 代码里，没有反汇编。
   它是否还做别的校验（比如检查变量是否在白名单），只能实测。
4. **AMD SME/TSME 若开启**，SMM 读到的明文内存与 CPU 看到的加密内存不一致，
   报文会失效。消费级笔记本默认不开，但这是未知项。
5. **`EBX="O2H$"` 是魔数不是握手**。如果这版固件改了魔数，`out` 会静默失败。

## 10. 为什么不做成内核模块

可以做，而且更干净（直接 `__get_free_pages` 拿物理地址，不用 pagemap 和迁移复核）。
没做的原因：

- 内核模块要跟内核版本绑定，Arch 每次升级都要重编，维护成本高
- 用户态 + 一页锁住的内存已经足够，`mlock` + 发送前复核把窗口压到微秒级
- 出问题时 `dmesg` 里多一个 tainted 标记，不值得

如果你要长期高频使用这条通道，写模块是更合适的选择。
